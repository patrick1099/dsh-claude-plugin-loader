# 0.2.0 真机验证记录（hooks 桥）

本文件记录 0.2.0 hooks 桥在本机的真机验证方式与结果。验证使用**独立临时 profile**，
没有重启也没有改动 `desktop` profile；`desktop` 会话仍在运行时完成。

## 环境

- Windows 10 19045，Node v24.22.2（`dsh` CLI 0.1.0-rc.8），Python 3.14.6（`py -3`）。
- 本机 `desktop` profile 由 DeepSeek Harness 桌面版占用；验证全程未触碰。
- 注意：npm 全局 `dsh` CLI 是 0.1.0-rc.8，而桌面版写出的 `~/.dsh/.credentials.yaml` 是新格式
  （扁平映射），rc.8 解析失败。验证 profile 用 `credentials-local.path` 指向一份**临时只读副本**
  （从原文件读取 `DEEPSEEK_API_KEY`，不修改原文件、不打印明文）。

## 临时 profile 与测试插件

```text
~/.dsh/profiles/loader-e2e-a/   # DSH 原生通道
  package.json                  # bundles: @deepseek-ai/dsh-base + @deepseek-ai/dsh-headless
  cordis.patch.yml              # loader insert + session/credentials 指向 temp
  dsh-claude-plugin-loader.mjs  # 本仓单文件复制
  e2e-end-driver.mjs            # 宿主侧一次性 agent create→dispose（SessionEnd 取证）

~/.dsh/profiles/loader-e2e-b/   # Claude 兼容通道（含真实 vibe-flow doc_gate.py）

%TEMP%/loader-e2e/
  plugins-a/hook-probe/         # .claude-plugin/plugin.json + hooks/dsh.json（六个事件）
  plugins-b/claude-vibe-gate/   # hooks/hooks.json：Stop=真实 doc_gate.py；SessionStart=探针
  ws-a, ws-b/                   # 会话工作区
  sessions-a, sessions-b/       # 重定向的会话持久化根
  hooks-a.jsonl, hooks-b.jsonl  # loader 的 hook 执行日志（本次验证的 hookLogPath）
  markers/events/*.json         # 测试 hook 每次调用的独立 marker
  evidence/                     # 归档：run 日志、hook 日志、markers、会话日志（zstd+解码）
```

测试插件的 hook 脚本是临时目录里的 `.py`（不是仓库的一部分），每次调用写一份
`markers/events/<时间>-<pid>-<event>.json`，避免并发 hook 抢同一个追加点。

## 命令

```powershell
# A：DSH 原生通道
cd %TEMP%/loader-e2e/ws-a
dsh --profile loader-e2e-a "<六步任务：write / 被 deny 再重试 / read 被 PostToolUse 阻断 / stop-ack>"

# B：Claude 兼容通道 + 真实 vibe-flow 文档闸
cd %TEMP%/loader-e2e/ws-b
dsh --profile loader-e2e-b "<改 code.py → 被 Stop 文档闸拦 → 补 docs → 收工>"
```

两个 profile 的 `cordis.patch.yml` 都把 `dsh-session-persistence-jsonl.root` 指到 temp，
并设置 loader 的 `sessionRoot` / `hookLogPath` 指向 temp，避免污染用户会话库。

## 结果

### A：六个 dsh 事件全部真实触发

`markers/events` + `hooks-a.jsonl` 可见（一次短任务的量）：

| 事件 | 次数 | 证据 |
|---|---|---|
| `agent/created` | 1 | stdin 含 `source=startup`（loader 对 created 推断 source） |
| `agent/session-start` | 1 | `source=startup`，与 created 同批去重，未重复 start |
| `agent/inbox/inserted` | 1 | `prompt` = 任务全文 |
| `tools/pre-execute` | N | `tool_name` 为 dsh 原生名（`write`/`pwsh`/`read`） |
| `tools/post-execute` | N | `tool_response={is_error,content,value}` |
| `agent/turn-stopping` | 2 | 第一次 `stop_hook_active=false`（block→steer），第二次 `true`（放行） |
| `agent/disposed` | 1 | 由 e2e-end-driver 的一次性 agent `create→dispose` 触发（真实注册表事件） |

拦截三态：

- **放行**：普通 `write`/`read` 调用 → hook 返回空 → `decision=none`；
- **拒绝**：第一次 `write …/deny-once.txt` → hook 返回 `permissionDecision:"deny"`，
  工具结果里出现 `PROBE-DENY: …`，`hooks-a.jsonl` 记 `decision=deny`；
- **解除后恢复**：同一路径重试 → `decision=none`，写入成功；
- **PostToolUse 阻断**：一次 `read` 的结果被 `decision:block` 改成错误，下一次 read 正常。

注入真实性：hook 注入随机 nonce，模型最终回答里出现同一 `HOOK-NONCE=<32hex>`
（值只存在于 hook 的 state 文件与注入上下文里），证明 `additionalContext` 真的进入模型上下文。

### B：Claude 兼容通道复用真实 vibe-flow 文档闸

`ws-b/vibeproj` 是一个 git 仓（`code.py` + `docs/BLUEPRINT.md` + `docs/CHANGELOG.md`，
docs 的 mtime 比 code 早 2 小时）。任务：改 `code.py`，等文档闸。

结果：

- `hooks-b.jsonl`：
  `agent/session-start decision=context` →
  `agent/turn-stopping decision=block`（真实 `doc_gate.py`，711ms）→
  同一 turn 第二次 `agent/turn-stopping decision=none`（`stop_hook_active=true`，doc_gate 直接放行）；
- 会话日志里出现 loader 注入的 steer 消息，内容正是 doc_gate 的 `{"decision":"block","reason":"[vibe-flow 文档闸] …"}`；
- 模型最终回答含 `VIBE-DOC-GATE-SEEN`、`DOCS-UPDATED`、`HOOK-NONCE=<32hex>`；
- 模型随后用 edit 更新了两份 docs（会话日志里可见 edit 调用到 `docs/CHANGELOG.md`、`docs/BLUEPRINT.md`）。

也就是说：Claude 通道合成的 `transcript_path` 被真实 `doc_gate.py`（`locate.py` 的
`read_rows/content_items/last_prompt_index/touched`）成功解析，Stop 协议翻译为 `agent.steer` 生效。

## 环境噪声（与 hook 判定无关）

本机 Esafenet 透明加密把 temp 里的 `.py` 也当作密文容器：DSH 的 `write`/`edit` 对它们会报
`EXDEV: cross-device link not permitted` / `ReplaceFileW EIO (Win32 1175)`。模型改用 `pwsh`
或 `esafe-code` 落盘；hook 的 deny/allow/block 判定均在真实工具调用上发生，未受影响。
这也是为什么 e2e 里"文件最终内容"由 pwsh/esafe-code 写入，但 hook 证据仍然成立。

## 已知限制（见 README「已知限制」）

- one-shot headless 完成任务后直接退出，不会 dispose 主 agent；SessionEnd 只在长生命周期宿主
  （desktop/web/tui）正常 dispose 时触发。本验证用宿主侧一次性 agent 取得真实
  `agent/disposed` 回调。
- UserPromptSubmit 无法硬阻断（dsh `agent/inbox/inserted` 是只读通知）。
- `clear` / `compact` 这两个 source 只有 `agent/session-start` 能提供。
